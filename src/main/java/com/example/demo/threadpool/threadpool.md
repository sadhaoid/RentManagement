# 线程池练习：基于 `ThreadPoolPractice.java` 的改造指南

> 不新建代码，直接在项目已有的 `ThreadPoolPractice` 基础上改造——它本身就藏着好几个值得挖的问题，比空手写一个新例子更有实战感。

## 第一步：诊断——这份代码现在有几个问题，自己找一遍

在动手改之前，自己对着现有代码问自己以下几个问题，想清楚了再往下走：

1. `Executors.newFixedThreadPool(4)` 这一行，在阿里巴巴 Java 开发手册里是被明确不推荐的写法。**你知道为什么吗？**
   > 提示：点进 `newFixedThreadPool` 的源码看它内部到底 `new` 了一个什么样的 `ThreadPoolExecutor`，尤其注意它传的那个队列参数——那个队列的容量上限是多少？这意味着什么风险？

2. 这个类完全没有 `@Component`，也没有在任何地方被 `@Bean` 注册进 Spring 容器。**现在这段代码在项目里实际上处于什么状态？**（它会不会被执行到？）

3. `threadPool()` 方法每次被调用，都会 `new` 一个全新的线程池出来，用完只 `shutdown()`。**如果这个方法未来被做成一个 HTTP 接口，被高频调用，会发生什么问题？**
   > 提示：线程池的创建本身是有开销的，频繁创建销毁和"复用一个常驻线程池"比，哪个更符合线程池这个设计本身想解决的问题？

4. `CountDownLatch countDownLatch = new CountDownLatch(4)` 这个计数固定写死成 4，和 `partitionContract()` 切出来的分片数量（`lists.size()`）之间，**有没有可能对不上？** 如果 `lists.size()` 因为数据量变化不再是 4，会发生什么？

想清楚这四个问题（不用现在都能答对，但要先自己琢磨过），接下来一步步把它们解决掉。

## Step 1：把 `Executors.newFixedThreadPool` 换成手动 `ThreadPoolExecutor`

自己去看一下 `ThreadPoolExecutor` 的构造函数，它需要传这几个参数，自己对照着想每个参数该填多少、为什么：

- **核心线程数（corePoolSize）**：平时保留的线程数，想一下你的场景（CPU 密集型过滤 + 内存操作，没有远程 IO 阻塞）大概设成几比较合理，可以先照抄原来的 `4`
- **最大线程数（maximumPoolSize）**：比核心线程数大多少合适，先想清楚"什么情况下线程池会用到超过核心线程数的线程"
  > 提示：跟你接下来要选的队列类型直接相关

- **空闲线程存活时间（keepAliveTime）** + 时间单位
- **工作队列**：不要用 `Executors` 内部默认的那种无界队列，自己选一个**有界**的阻塞队列类型，想一下为什么"有界"对生产场景更安全（回忆一下诊断问题 1）
- **拒绝策略**：队列满了、线程也到了最大值，新任务该怎么办？Java 自带几种策略，自己查一下 `AbortPolicy`（直接抛异常拒绝）和 `CallerRunsPolicy`（让提交任务的那个线程自己去执行这个任务，变相起到"降速"的效果）这两种的区别，先选一个用，想清楚选它的理由

---

## Step 2：把这个线程池变成一个"常驻"的 Spring Bean

自己想一下：线程池这种资源，应该是"每次用的时候现造一个用完就扔"，还是"整个应用生命周期里只造一次、大家共用"？

动手把 `ThreadPoolPractice` 里 new 线程池那部分逻辑，搬到一个**配置类**里，用 `@Bean` 的方式把这个 `ThreadPoolExecutor` 注册成一个 Spring 容器管理的单例对象，然后在 `ThreadPoolPractice`（记得给它也加上 `@Component`，不然它自己也不会被 Spring 管理）里通过构造函数注入这个 Bean，而不是在方法内部 `new`。

**想一个问题**：Spring 容器管理的 Bean，在应用关闭的时候有没有办法执行一段"清理"逻辑？
> 提示：搜一下 `@PreDestroy` 注解，或者 `ThreadPoolExecutor` 有没有实现某个和"销毁"相关的接口——线程池这种资源，应用关闭时应该怎么优雅地收尾，不要留着不管。

## Step 3：修掉 `CountDownLatch` 数量写死的问题

想清楚：`CountDownLatch` 的计数值，本质上应该等于"你总共提交了多少个任务，需要等它们都完成"。现在这个数字应该从哪里动态获取，而不是写死 `4`？自己改一行代码解决它。

**顺带想一个更深的问题**：如果某个分片任务在执行过程中抛出了异常，`countDownLatch.countDown()` 这行代码还会不会被执行到？如果不会，`countDownLatch.await()` 会发生什么？
> 这是给你留到 Step 5 处理异常时候的伏笔，先想着，不用现在解决。

## Step 4：写一个真正的性能对比实验

这一步是把线程池的价值**用数字证明给自己看**，而不是背书说"线程池能提高并发性能"。

自己写一个对比方法：同样一份数据（可以直接复用 `partitionContract()` 切出来的分片），分别用：

- **单线程**顺序遍历所有分片，执行同样的过滤逻辑，记录耗时（`System.currentTimeMillis()` 或更精确的 `System.nanoTime()`）
- **线程池并行**执行（就是现在这套逻辑），记录耗时

打印出两个耗时对比。**想一下**：如果你的数据量不够大（比如只有几千条），两者耗时会不会看不出明显差异，甚至线程池版本因为线程调度开销反而更慢？这提醒你什么道理——线程池不是任何场景下都比单线程快，只有在**任务量足够大、单个任务有一定计算量**时，并行的收益才能覆盖掉线程调度本身的开销。用 `DataCreator` 里能生成的数据规模去跑一下，自己找到这个"分水岭"大概在什么量级。
